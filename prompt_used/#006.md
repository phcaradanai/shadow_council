# Main Objective

Build a working foundation supporting this minimum flow:

Create Room
→ Join Room
→ Start Match
→ Initialize authoritative game state
→ Deliver correct public/private player state
→ Submit gameplay intent
→ Validate intent
→ Allow required reaction
→ Resolve action in Game Engine
→ Emit domain events
→ Update authoritative state
→ Synchronize clients
→ End round

The result must be runnable and testable.

Do not implement the full game yet.

# Phase 1 — Domain Foundation

Implement the minimum domain model necessary for one match.

Likely concepts include:

* Match
* MatchId
* Player
* PlayerId
* GameState
* MatchPhase
* Resource state
* Action
* Reaction
* Target
* Domain Event

Use the approved terminology from `DOMAIN_MODEL.md`.

Do not invent additional domain concepts without need.

---

# State Machine

Implement the approved match state machine.

Every transition must be explicit.

Example only:

LOBBY
→ SETUP
→ ROUND_START
→ ACTION_SELECTION
→ REACTION
→ REVEAL
→ RESOLUTION
→ ROUND_END

Use the actual approved states.

The engine must reject commands that are invalid for the current phase.

Example:

A player cannot submit an action while the match is still in Lobby.

---

# Domain Commands

Represent gameplay intent explicitly.

Examples:

* CreateMatch
* JoinMatch
* StartMatch
* CommitAction
* CommitReaction

Use the actual approved contracts.

Commands describe player intent.

They must not contain calculated authoritative outcomes.

BAD:

`damage: 3`

GOOD:

`action: Strike`
`target: playerB`
`committedPower: 3`

---

# Game Engine

Create a clear authoritative Game Engine entry point.

It must:

1. receive validated command/context
2. check current state
3. validate game rules
4. resolve gameplay
5. produce new state
6. produce domain events

Prefer an API conceptually similar to:

`execute(state, command) -> result`

where result contains:

* new state
* emitted events
* failure when invalid

Exact implementation should follow the approved architecture.

Avoid a giant `GameEngine` class.

Separate responsibilities when they genuinely differ.

---

# Deterministic State

Authoritative game behavior must be deterministic where specified.

Introduce the approved seeded:

`RandomProvider`

Do not scatter:

`Math.random()`

through gameplay code.

The engine should later support:

initial state

* seed
* ordered commands
  = reproducible result

# Phase 2 — Application Layer

Implement the application orchestration required to operate a match.

Responsibilities may include:

* create room
* join room
* start match
* submit command
* get public state
* get private player state
* manage player ownership/session mapping
* invoke Game Engine
* persist state through an interface
* publish resulting events/state changes

Application services must not duplicate domain rules.

---

# State Visibility

Design explicit projections/views.

The authoritative state may contain private information.

Never send the full state to every player and merely hide fields in the UI.

Create outputs such as:

`PublicGameView`

and

`PlayerPrivateView`

or the approved equivalent.

Verify that Player A cannot receive Player B's hidden information.

---

# Phase 3 — Infrastructure

Implement only infrastructure required by the first vertical slice.

Possible adapters:

* in-memory match repository
* seeded random implementation
* HTTP transport
* realtime transport
* session/player mapping

For the first implementation, prefer:

> in-memory persistence before a database

unless the approved ADR explicitly requires persistence now.

Do not add production database complexity before gameplay requires it.

---

# Realtime Synchronization

Implement the simplest reliable realtime mechanism approved by architecture.

The server must remain authoritative.

Clients should receive:

* public state changes
* player-specific private state
* required reaction prompts
* domain-driven reveal/result events

Do not expose private information in broadcast messages.

Design event/message contracts explicitly.

---

# Phase 4 — Minimal Presentation

Build only enough UI to play and debug the vertical slice.

Required minimum may include:

## Lobby

* create room
* join via room code
* show players
* start match

## Game

* current phase
* players
* own resources
* allowed actions
* choose target
* commit action
* reaction prompt
* reveal/result
* round state

Do not build polished visual design yet.

Do not build animation systems yet.

Correct gameplay state is more important.

---

# UI Rule

The UI may determine:

"What should I render?"

It must not determine:

"What is the authoritative result?"

Example:

GOOD:

Server says:

`AttackResolved`

UI renders the result.

BAD:

UI calculates whether Strike beats Guard.

# Phase 6 — Tests

Tests are mandatory.

## Domain Unit Tests

Cover at least:

* state transitions
* command validity by phase
* valid action
* invalid action
* insufficient resource
* target validation
* reaction validation
* resolution result
* emitted events
* deterministic behavior

## Scenario Tests

Create readable gameplay scenarios.

Example:

Given:
Player A and Player B are active.

When:
A commits Strike against B.
B commits Guard.

Then:
the action resolves according to approved MVP rules.

Use actual approved gameplay rules.

## Application Tests

Test:

* room creation
* joining
* starting
* player ownership
* command routing
* state projection
* hidden information isolation

## Minimal E2E

Prove:

Create Room
→ second player joins
→ match starts
→ action submitted
→ reaction submitted
→ server resolves
→ both clients receive correct result

One working vertical slice is more valuable than dozens of incomplete tests.

# Definition of First Milestone

Milestone 1 is complete when two or more local clients can:

1. create/join the same match
2. start the match
3. receive different player-specific private views
4. perform one complete approved action/reaction interaction
5. have the server resolve it authoritatively
6. receive the correct result
7. advance to the next valid game state

And:

* domain tests pass
* scenario tests pass
* application tests pass
* E2E passes
* lint passes
* typecheck passes
* build passes
* architecture checks pass
