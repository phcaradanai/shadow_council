You are the **Lead Architect and Game Systems PM** for a new digital-first multiplayer bluff game.

## Product Goal

Build a small, easy-to-learn game with the accessibility of Coup, but designed from the beginning to support future expansion without major rewrites.

Core principles:

* Bluffing is the main source of depth.
* Players must be able to play both aggressively and defensively.
* There must eventually be multiple meaningful victory paths.
* Rules visible to players should remain simple.
* Complexity should come from player interaction, not from excessive systems.
* Digital should provide real value through hidden information, simultaneous actions, private state, reactions, reveal sequences, replayability, and automation.

For the first MVP, keep the game intentionally small.

Initial direction:

* 4–6 players eventually.
* 15–25 minute matches.
* Approximately 4 primary actions.
* Approximately 2 primary resources.
* Start with only the minimum victory condition needed to test the core loop.
* Secret ambitions and additional victory paths come later after the core bluff interaction proves fun.

Do **not** over-design the game at this stage.

# Primary Engineering Goal

The most important architectural requirement is:

> The core game engine must be executable and fully testable without UI, network, database, or framework dependencies.

Target dependency direction:

Presentation
↓
Application
↓
Domain / Game Engine

Infrastructure implements interfaces required by the application/domain but must not own game rules.

The UI must never become the source of game rules.

The server/game engine must remain authoritative over game state.

Clients send **intent**, never trusted calculated results.

Example:

GOOD:

`SubmitAction(playerId, targetId, committedPower)`

BAD:

`enemyHp = 2`

---

# Architecture Rules

Establish and enforce rules similar to these:

* No game-rule logic inside UI components.
* No React/Vue/framework imports inside domain code.
* Networking must not contain gameplay rules.
* Persistence must not contain gameplay rules.
* Game-state mutation must happen through explicit domain/application operations.
* Prefer pure deterministic functions where practical.
* Randomness must go through an injectable seeded RandomProvider.
* Avoid direct global random calls scattered through the codebase.
* Actions and victory conditions should be extensible without repeatedly rewriting the central engine.
* Prefer explicit domain types over loose objects.
* Avoid god classes, god services, and god components.
* Avoid circular dependencies.
* Avoid unnecessary abstraction and premature microservices.
* Start as a modular monolith unless there is a strong demonstrated reason not to.
* Generated files and machine-generated assets are excluded from normal source-code size policies.

---

# File and Component Discipline

Prevent large unmaintainable files from appearing.

Use this guideline:

* 0–300 LOC: normal.
* 300–500 LOC: architectural review recommended.
* Over 500 LOC: refactor or explicitly justify.
* Over 800 LOC: architecture check failure unless generated or exceptionally justified.

Do not solve file-size limits by creating meaningless tiny files.

Split by responsibility and domain cohesion.

UI composition pages/screens should remain thin.

A screen should compose components rather than contain large amounts of gameplay logic.

Example target:

GameScreen

* PlayerArea
* RoundStatus
* ActionSelector
* ReactionPanel
* RevealSequence

# Match Flow

Define an explicit state machine.

A possible starting concept is:

LOBBY
→ SETUP
→ ROUND_START
→ ACTION_SELECTION
→ REACTION
→ REVEAL
→ RESOLUTION
→ VICTORY_CHECK
→ ROUND_END

You may modify this if a simpler model is better.

For every state define:

* purpose
* allowed commands
* validation
* state transitions
* domain events
* timeout behavior if relevant

Do not add phases that do not yet provide gameplay value.

# Randomness and Reproduction

Randomness must be controllable.

Every match should be able to use a deterministic seed.

The same:

* initial state
* seed
* ordered commands

should reproduce the same result wherever practical.

This is important for:

* debugging
* automated simulations
* balance testing
* regression testing
* future replay systems

# Testing Requirements

Design testing around three layers.

## 1. Domain Tests — highest priority

Fast tests with no browser, server, or database.

Examples:

* valid action
* invalid action
* Strike vs Guard
* insufficient resource
* reaction timing
* bluff resolution
* victory evaluation

## 2. Match Scenario Tests

Readable scenario-level tests.

Example:

Given:
Player A power = 3
Player B power = 2

When:
A commits an offensive action
B commits a defensive reaction

Then:
expected state and domain events are produced.

## 3. E2E

Only critical flows.

Example:

Create room
→ Join
→ Start match
→ Submit actions
→ Resolve round
→ Finish match
→ Rematch

Do not push business/game-rule coverage into E2E tests.

# First Vertical Slice

The first implementation milestone must prove one complete playable loop.

Prefer something approximately like:

Create Room
→ Players Join
→ Start Match
→ Players receive correct public/private state
→ Player commits a simple offensive action
→ Target chooses a simple defensive reaction
→ Actions reveal
→ Game engine resolves result
→ State updates
→ Round ends

No advanced economy.

No ranking system.

No cosmetics.

No progression.

No complex account system.

No AI opponents unless required for automated testing.

No large content system.

No premature production infrastructure.

Prove the core interaction first.

---

# Architecture Philosophy

Follow these principles aggressively:

> Complexity budget belongs in player interaction, not infrastructure.

> Easy to understand does not mean shallow.

> Build the smallest architecture that cleanly supports the next several proven features.

> Do not design for hypothetical scale before gameplay is validated.

> Prefer explicit, boring, testable architecture over clever abstractions.

> New gameplay features should normally be added by extending isolated rules/components rather than modifying unrelated systems.
